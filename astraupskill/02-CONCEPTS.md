# 02 - Concepts that make the workflow safe

An enrollment is a snapshot of learner context. It stores `userId`, `organizationId`, `courseId`, and `courseVersionId`. Every learner write must prove all three scopes: the actor owns the enrollment, the enrollment belongs to the selected organization, and the content ID belongs to the enrolled version. Checking only `courseId` would let a learner submit a quiz from a draft or from an unrelated version of the same course.

Published selection has two parts. The course query requires `status: "PUBLISHED"`; the version query requires `id: course.currentVersionId`, `courseId: course.id`, and `status: "PUBLISHED"`. This prevents a stale pointer, a draft pointer, or a version from another course from being enrolled. Existing enrollments do not move when `currentVersionId` later changes. Their completion rule comes from the included `courseVersion`, which is why version ownership is part of the completion proof.

The completion rule is a set of obligations. With `requireAllLessons: true`, every ID in `requiredLessonIds` needs a `COMPLETED` progress row. If an ID is absent from progress, `some(...)` is false and completion stops. With `requiredQuizIds`, every listed quiz needs at least one passed attempt meeting `minimumQuizScore` when configured. With `requiredAssignmentIds`, every listed assignment needs a `GRADED` submission. Explicit empty arrays mean no items are configured, so a course can validly have no assessments; omitted arrays mean the route may derive IDs from the enrolled version when the corresponding broad flag is enabled. This difference prevents `.every([])` from silently satisfying a required set.

Progress timestamps distinguish the initial start from the current completion state. The first write sets `startedAt` if it is null. A repeated `COMPLETED` write preserves an existing `completedAt`; moving back to `IN_PROGRESS` clears `completedAt` while leaving `startedAt` intact (lines 125-126 of the learner router). Review this as an API policy before changing it; the route does not invent a separate event-sourcing timeline.

Side effects are grouped with their business write by passing the Prisma transaction client to `auditLog` or `recordDomainEvent`. The event helper creates both `DomainEvent` and `OutboxMessage` on that client. The outbox is a durable database record for a later worker; the current route does not claim delivery, retries, or a worker implementation. Completion replay is stable because a `COMPLETED` enrollment returns its existing certificate and does not create another certificate, audit, or event. The route tests verify this contract with spies; a real database test would still be needed for rollback and races.

There are two useful distinctions when reviewing a rule. An omitted `requiredQuizIds` can be derived from the enrolled version when `minimumQuizScore` is present; an explicit `requiredQuizIds: []` says that no quiz is required. Likewise, `requireAssignmentsGraded: true` with no explicit assignment IDs derives all assignments in the enrolled version, while an explicit empty list leaves the set empty. This is a data-model decision, not a JavaScript trick. If a future author changes parsing to coalesce every empty array to `undefined`, a no-assessment course silently becomes assessment-bound. Keep a test for both forms next to any parser change.

Explicit requiredLessonIds and requiredAssignmentIds are enforced whenever supplied, even if the broad boolean is false. In legacy domain calls with no explicit IDs, requireAllLessons requires nonempty progress with every row completed; the API supplies the enrolled version’s IDs when deriving all lessons, so a missing row cannot disappear from that comparison. An explicitly empty list overrides the broad flag. Completion and certificate eligibility are separate: a rule can permit completion without all lesson rows complete, while the existing certificate helper still requires 100 percent of materialized progress. A course with no lesson progress has zero percent and can complete under empty requirements without receiving a certificate.

## What the OutboxMessage row is for

`recordDomainEvent` (`apps/api/src/events.ts`) writes a `DomainEvent` and an `OutboxMessage` on the transaction client, so the message exists exactly when the business write commits. Nothing in `apps/api` sends it. The only consumer is the `outbox-dispatch` BullMQ worker in `apps/worker/src/worker.ts` (lines 52-73), and it is a placeholder: it reads 25 `PENDING` rows and marks each `SENT` without publishing anything, and with no lease or row lock, so two workers would process the same rows. Treat the outbox here as "durably recorded", not "delivered".

A real relay must, in order: claim a batch (`SELECT ... FOR UPDATE SKIP LOCKED` plus a lease timestamp); publish each message; mark it sent; and let an expired lease be retried by another worker. Delivery is then *at least once*, and consumers must de-duplicate by message id. Predict what happens if the worker marks the row sent *before* publishing (a lost message on crash) versus after (a duplicate on crash), and why the duplicate is the right failure to choose.
